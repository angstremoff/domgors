# Полный план: сжатие фото в web (Canvas API + прогресс-индикатор, БЕЗ зависания)

## Контекст
Git-история: сжатия в web **никогда не было** (0 совпадений по всем коммитам). Грузятся raw-файлы. Создаём сжатие с нуля.

## Ключевое UX-требование
Пользователь НЕ должен воспринимать процесс как зависание. Решение: **прогресс-индикатор с счётчиком** «Обработка фото 3/12» поверх галереи + отзывчивый UI.

## Архитектурное решение: Web Worker ОТВЕРГНУТ
Воркеры в проекте **никогда не использовались** (0 следов: нет `new Worker`, нет worker-зависимостей, нет конфигурации в next.config). Вводить сейчас = новая инфраструктура (worker-bundling в Next.js static export, edge-cases с типами, отладка) = **повышение риска регрессий**, что противоречит требованию. 

Альтернатива, дающая тот же UX-эффект без риска: **async/await цикл** с `await` между фото — браузер может перерисовывать UI (анимация спиннера, прогресс) в микротасках. Canvas-сжатие одного фото при 1280px/0.7 — ~100-300мс, между фото UI свободен. Плюс явный счётчик прогресса снимает восприятие «зависания».

## Принципы (без регрессий)
1. **Сжатие при отправке** — state/preview/cleanup/reorder/handleFiles НЕ трогаем.
2. **Прогресс-индикатор** — переиспользуем существующий overlay-паттерн `bg-black/50` над галереей + `Loader2 animate-spin` (уже в проекте).
3. **Строго аддитивно** — 1 новый модуль + правки в upload-циклах. Ничего не удаляется.
4. **Graceful fallback** — при ошибке сжатия грузится оригинал (как сейчас).
5. Порядок фото сохраняется; существующие в Edit НЕ пережимаются.

## Параметры сжатия (референс mobile)
Canvas API, 1280px (пропорционально), JPEG 0.7, выход всегда `.jpg`/`image/jpeg`. Порог < 50KB — пропустить.

---

## 1. Модуль `web/lib/imageCompression.ts` (НОВЫЙ)
Чистая функция, без зависимостей, только браузерный Canvas API:
```ts
export interface CompressedImage {
  blob: Blob; contentType: string; extension: string; compressed: boolean;
}
export async function compressImageFile(file: File): Promise<CompressedImage>
```
Логика: `createImageBitmap` → canvas (пропорциональный ресайз до 1280px) → `toBlob('image/jpeg', 0.7)`. Если сжатый > оригинала или ошибка → вернуть оригинал (`compressed:false`). Cleanup `bitmap.close()`.

## 2. Прогресс — callback в compressImageFile (опционально) ИЛИ внешний счётчик
Прогресс ведётся **в самой upload-функции** (не в модуле сжатия) — простой счётчик `i / total`. Это изолирует модуль сжатия от UI.

## 3. `AddPropertyForm.tsx`
- **State** (новый, аддитивно): `const [photoProgress, setPhotoProgress] = useState<{current:number; total:number} | null>(null);`
- **uploadImages** (стр. 366-391): перед циклом `setPhotoProgress({current:0, total:files.length})`, в цикле `setPhotoProgress({current:i+1, total:files.length})`, сжатие `compressImageFile(item.file)` → `.upload(compressed.blob, {contentType: compressed.contentType})`, после — `setPhotoProgress(null)`.
- **UI overlay** над галереей фото (стр. ~955, внутри `Card ref={photosRef}`): при `photoProgress` — overlay `absolute inset-0 ... bg-black/50 flex items-center justify-center` со спиннером `Loader2 animate-spin` + текст `t('property.addProperty.photosProcessing')` + `${current}/${total}`. Переиспользует существующий паттерн overlay-бара.
- Кнопка submit: текст меняется на «Обработка...» при `photoProgress` (рядом со спиннером, уже есть). Сейчас только `Loader2` без текста — добавлю динамический текст.
